# Secondary rules

Rules every agent follows in addition to the five in [`AGENTS.md`](../AGENTS.md#rules-to-live-by). Read this file before starting any work.

- **Spec authoring**: before writing or editing a file under `specs/`, read its rules file from [`specs/rules/README.md`](specs/rules/README.md) (`author-spec` skill). Do not copy those rules into the spec. CI `Spec lint` checks the structural rules ([`docs/spec-lint.md`](../docs/spec-lint.md)). When applying a failed spec review, follow [`specs/alignment.md`](specs/alignment.md).
- **Quality rubrics**: characteristics in [`specs/definition/quality.md`](../specs/definition/quality.md) are the source of truth. Axes and evaluators live in [`specs/definition/quality/rubrics.md`](../specs/definition/quality/rubrics.md). Guide the owner with `author-quality-rubrics`. Deterministic axes are the verification obligation. Qualitative axes are judged at acceptance. `run-quality-evaluators` executes them: deterministic during verification, `llm-judge` during acceptance. Acceptance reuses a passing deterministic record while `game/` matches the recorded commit ([evidence README](../docs/quality/evidence/README.md)) and does not re-run those checks.
- **Spec depth**: `specs/definition/definition.md` sets `prototype`, `small`, or `full`, which scales story coverage and diagrams per [`specs/rules/depth.md`](specs/rules/depth.md). Screen and journey mockups are always required.
- **UX mockups and main-tree UI**: HTML mockups under `specs/ux/mockups/` bind main-tree UI (layout, palette, close functional tracking; not pixel-perfect). Catalog approval gates UI implementation. Contract: [`docs/ux-mockups.md`](../docs/ux-mockups.md).
- **Spec review**: review a spec with the `review-spec` skill, using the checklist linked from [`specs/README.md`](../specs/README.md) and [`specs/alignment.md`](specs/alignment.md). Whole-spec review also runs `audit-spec-applicability`, `audit-spec-terminology`, and `audit-spec-tbd`; any Fail fails the overall verdict.
- **Architecture decisions**: engine, framework, library, storage, integration, and game-architecture choices are ADRs in [`specs/adr/`](../specs/adr/adr.md). The engine itself is chosen in [`specs/definition/definition.md`](../specs/definition/definition.md); its Engine ADR realizes that choice. Only Accepted ADRs authorize code. Do not read `specs/adr/archive/` unless explicitly asked.
- **Playtesting**: AI-agent playtests against design and UX per [`specs/playtest/`](../specs/playtest/playtest.md); in-repo index under [`docs/playtest/evidence/`](../docs/playtest/evidence/); screenshots and logs on the repo wiki ([`wiki-evidence.md`](../docs/playtest/wiki-evidence.md)). Required at acceptance only when deliverables change playable behavior. A headless run may judge without screenshots and must not file a defect for that gap; acceptance waits until a graphical re-run of the same build supplies the screenshots the protocol requires.
- **Aesthetics and assets**: the game's style (medium, pillars, palette, form, motion, interface and sound style) lives in [`specs/aesthetics/`](../specs/aesthetics/aesthetics.md), downstream of definition, quality, design, and view. Asset kinds, tool roles, procedures, style series, and the catalog live in [`specs/assets/`](../specs/assets/assets.md). Identity for a kind uses three pillars: enforced styling (anchors + hard binding or soft exemplars), master/negative `prompt_policy`, and review (look or listen). Visual series use Recraft; music / SFX / voice use the ElevenLabs CLI (SFX soft-enforce until a durable style API exists; never ElevenLabs MCP). Establish or refresh a kind series with `establish-asset-style` (`APR.establish-style`); generate/update/touch-up with `manage-asset`. Most generation tools are Integration ADRs; [`docs/asset-tools.md`](../docs/asset-tools.md) marks Recraft and ElevenLabs ADR-free and **required** for their modality's style-series establish and style-constrained generate; Cheaper Inference is ADR-free for non-series visual generate / reference-anchor (locked steps + `.github/scripts/cheaperinference_image.py`); fal.ai is high-throughput raw image host when the visual series is not `active`. Agent generation is optional. Tools that doc bans (Pixellab) are never used. Catalog person-supplied assets with `register-asset`; review with `review-asset`. Only a person may exempt an asset from review, one at a time, recorded in the catalog. Every asset has a permanent asset ID (UUID version 7 from `.github/scripts/new_asset_id.py`, never typed) and a unique handle `<kind-spec>/<name>`, in one JSON entry file per asset that CI checks (`asset_catalog.py`).
- **Technical design**: code and data shape (layers, modules, components, contracts, schemata, sequences) live in [`specs/technical/`](../specs/technical/technical.md), downstream of definition, design, view, UX, and Accepted ADRs.
- **Coding conventions**: project-specific conventions (naming, formatting, layout, errors, tests) and lint/format/unit-test/coverage tooling live in [`docs/coding-conventions.md`](../docs/coding-conventions.md), owned by the project; template sync keeps its content. They are optional: a project may record `None — SOLID only` there. It extends [`docs/solid.md`](../docs/solid.md), owned by the template for every project, and never contradicts it. Precedence: SOLID, then conventions, then structure continuity. Every lint or format command it lists runs as a step in `Code lint` ([`code-lint.yml`](../.github/workflows/code-lint.yml)); unit-test and coverage commands run as `Unit tests` and `Coverage` ([`unit-tests.yml`](../.github/workflows/unit-tests.yml)). Wire those with `setup-unit-test-ci` (from `ensure-dev-env-setup`). Review a diff with `review-code`. Suggest structural refactors for the implementation tree or a named portion with `suggest-code-refactors`.
- **Concise docs/specs**: every file under `docs/` and `specs/` stays under **500 words**; split and link if longer. Issue-run Markdown under `docs/quality/evidence/issue-*` and `docs/playtest/evidence/issue-*` is exempt. CI enforces the cap (`Spec lint` `word-limit`). Details: [`docs/README.md`](../docs/README.md), [`specs/README.md`](../specs/README.md).
- **Demo mode and PoCs**: Product **demo** is a config-bounded mode of the main game ([`docs/demo.md`](../docs/demo.md), [`specs/design/demo.md`](../specs/design/demo.md)); Offering may stay TBD if none. **Specify, then build**: `capture-requirements` turns a game idea into specs. The user picks which files to fill and may revise a written requirement. A PoC under `pocs/<slug>/` is the alternative when the user asks to explore a named uncertainty ([`docs/pocs.md`](../docs/pocs.md)). Formalized specs constrain that PoC; placeholders and notes do not. Ask before any PoC pull request. A PoC is exempt from SOLID and coding conventions. Main code never imports it. A kept list returns through `reconcile-poc` / `promote-poc` ([`docs/poc-promotion.md`](../docs/poc-promotion.md)); spec depth is the bar for that slice. Already-specced main-tree work does not need a new PoC. Style/assets only when the PoC shows them ([`docs/poc-style-assets.md`](../docs/poc-style-assets.md)).
