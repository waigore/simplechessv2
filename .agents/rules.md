# Secondary rules

Rules every agent follows in addition to the five in [`AGENTS.md`](../AGENTS.md#rules-to-live-by). Read this file before starting any work.

- **Spec authoring**: before writing or editing a file under `specs/`, read its rules file from [`specs/rules/README.md`](specs/rules/README.md) (`author-spec` skill). Do not copy those rules into the spec. CI `Spec lint` checks the structural rules ([`docs/spec-lint.md`](../docs/spec-lint.md)). When applying a failed spec review, follow [`specs/alignment.md`](specs/alignment.md).
- **Spec depth**: `specs/definition/definition.md` sets `prototype`, `small`, or `full`, which scales story coverage, mockups, and diagrams per [`specs/rules/depth.md`](specs/rules/depth.md).
- **Spec review**: review a spec with the `review-spec` skill, using the checklist linked from [`specs/README.md`](../specs/README.md) and [`specs/alignment.md`](specs/alignment.md). Whole-spec review also runs `audit-spec-applicability`, `audit-spec-terminology`, and `audit-spec-tbd`; any Fail fails the overall verdict.
- **Architecture decisions**: engine, framework, library, storage, integration, and game-architecture choices are ADRs in [`specs/adr/`](../specs/adr/adr.md). The engine itself is chosen in [`specs/definition/definition.md`](../specs/definition/definition.md); its Engine ADR realizes that choice. Only Accepted ADRs authorize code. Do not read `specs/adr/archive/` unless explicitly asked.
- **Playtesting**: AI-agent playtests against design and UX per [`specs/playtest/`](../specs/playtest/playtest.md); evidence under [`docs/playtest/evidence/`](../docs/playtest/evidence/). Required at acceptance only when deliverables change playable behavior. A headless run may judge without screenshots and must not file a defect for that gap; acceptance waits until a graphical re-run of the same build supplies the screenshots the protocol requires.
- **Aesthetics and assets**: the game's style (medium, pillars, palette, form, motion, interface and sound style) lives in [`specs/aesthetics/`](../specs/aesthetics/aesthetics.md), downstream of definition, quality, design, and view. Asset kinds, tool roles, procedures, style series, and the catalog live in [`specs/assets/`](../specs/assets/assets.md). Identity for a kind uses three pillars: enforced styling (anchors + hard binding or soft exemplars), master/negative `prompt_policy`, and review (look or listen). Visual series use Recraft; music / SFX / voice use the ElevenLabs CLI (SFX soft-enforce until a durable style API exists, as does a third-party/human-made visual kind with no product style id; never ElevenLabs MCP). Establish or refresh a kind series with `establish-asset-style` (`APR.establish-style`); generate/update/touch-up with `manage-asset`. Most generation tools are Integration ADRs; [`docs/asset-tools.md`](../docs/asset-tools.md) marks Recraft and ElevenLabs ADR-free and **required** for their modality's style-series establish and style-constrained generate; fal.ai is high-throughput raw image host when the visual series is not `active`. Agent generation is optional. Tools that doc bans (Pixellab) are never used. Catalog person-supplied assets with `register-asset`; review with `review-asset`. Only a person may exempt an asset from review, one at a time, recorded in the catalog. Every asset has a permanent asset ID (UUID version 7 from `.github/scripts/new_asset_id.py`, never typed) and a unique handle `<kind-spec>/<name>`, in one JSON entry file per asset that CI checks (`asset_catalog.py`).
- **Technical design**: code and data shape (layers, modules, components, contracts, schemata, sequences) live in [`specs/technical/`](../specs/technical/technical.md), downstream of definition, design, view, UX, and Accepted ADRs.
- **Coding conventions**: project-specific conventions (naming, formatting, layout, errors, tests) and lint/format/unit-test/coverage tooling live in [`docs/coding-conventions.md`](../docs/coding-conventions.md), owned by the project; template sync keeps its content. They are optional: a project may record `None — SOLID only` there. It extends [`docs/solid.md`](../docs/solid.md), owned by the template for every project, and never contradicts it. Precedence: SOLID, then conventions, then structure continuity. Every lint or format command it lists runs as a step in `Code lint` ([`code-lint.yml`](../.github/workflows/code-lint.yml)); unit-test and coverage commands run as `Unit tests` and `Coverage` ([`unit-tests.yml`](../.github/workflows/unit-tests.yml)). Wire those with `setup-unit-test-ci` (from `ensure-dev-env-setup`). Review a diff with `review-code`. Suggest structural refactors for the implementation tree or a named portion with `suggest-code-refactors`.
- **Concise docs/specs**: every file under `docs/` and `specs/` stays under **500 words**; split and link if longer. CI enforces it for Markdown (`Spec lint` `word-limit` check). Details: [`docs/README.md`](../docs/README.md), [`specs/README.md`](../specs/README.md).
- **Gameplay demos**: build with `create-gameplay-demo` under `demos/<slug>/`. They are exempt from SOLID and the coding conventions but still spec first and spec-traced, and main code never imports them. Every demo is also a proof of concept for the style and the asset pipeline: it expresses `specs/aesthetics/` and uses only cataloged assets, each reviewed or exempted by a person ([`docs/demo-style-assets.md`](../docs/demo-style-assets.md)). To reuse demo behavior, use `promote-gameplay-demo` ([`docs/demos.md`](../docs/demos.md)).
